# 軽量なGUI・プロジェクト同期

読む条件: Codex/GUIの作品更新、変更検知、core/engine/UIの同期を実装するとき。
正本範囲: 同期処理の実行・排他・負荷・復旧ルール。具体的なAPIは実装段階で確定する。
関連要件: R-007, R-009, R-011。

Design status: ready

設計のみ。実装はplanned。現行の [APPLICATION](APPLICATION.md)、[SURFACE](SURFACE.md)、[HISTORY](HISTORY.md) の保証を拡張済みとは扱わない。初期実装では新しい分散イベント基盤や常設の履歴通知ログを追加しない。

## 優先順位

1. 別作品・別版を取り違えない。
2. 再生・停止・UI応答を同期の重い処理で妨げない。
3. 無変更時は何もしない。
4. 障害から再取得で復旧できる。

「常に連動」は通信断中の即時一致や演奏中の音の自動差替えではない。保存された作品、coreが受理した版、engineで再生中の版を照合し、未反映を反映済みと表示しないことを指す。

現行runtimeは約2秒ごとに作品一覧・文書を読み直す。共有選択の取得は起動時中心で、画像も再読込に伴って再取得する。この常時全取得を置き換える。同期追加を理由にpollを二重化しない。

同期対象はCodex/GUI等による共通Application API経由の変更だけとする。直接ファイル編集は対象外とし、ファイル監視・外部変更検知・取込・自動マージを設けない。APIによる資産登録や非同期jobの採用commitも対象に含む。

## 最小のデータ経路

Codex/GUIの編集 → 共通Applicationで検証・保存 → 対象の変更印を付ける → GUIが必要な表示だけ取得する。

GUIはファイルを独自解釈せず、coreが受理した表示snapshotを描く。engineも同じ受理版から再生する。曲名・BPM・種別、画像ID、波形の対象、再生sessionを一つの表示snapshotへまとめる。rendererは作品ファイルを書かない。

識別子は必要最小限とする。

| 識別子 | 用途 |
|---|---|
| project_idとrevision | 作品と保存版。編集はbase_revisionで競合拒否 |
| 選択対象 | project/song/version/comparison/過去revision。保存版とは別 |
| asset_id / 内容hash | 同revisionでも起きる画像・原音変更の検知とcache |
| playback_idと再生版 | 実際に鳴っている対象と適用確認 |
| runtime generation | 選択変更前に始めた非同期要求の結果を破棄 |

表示のsequenceはrenderer内の順序だけで、保存や実音反映の証明にはしない。これらから比較用のview keyを作るが、別の永続revision系統を増やさない。

## 排他・デッドロック防止

同期の読み取り、通知、描画はロックを取らない。保存済みのsnapshot/receiptを読む。途中更新を検知した読取は次の周期へ回し、無制限に整合読取を繰り返さない。

作品のmutationは既存の共通保存transactionへ集約する。新しい同期用ロックを重ねない。実装着手時に既存のlock呼出しを棚卸しし、同一呼出し経路で複数ロックを必要とする箇所は、外で検証・準備し、一つの保存lock内で競合確認と確定だけ行う形へ整理する。二重取得が残る入口に同期処理を追加しない。

ロック保持中は禁止: engine応答待ち、プラグイン起動、音声解析、画像デコード、ネットワーク、ユーザー入力、通知先の処理完了待ち、別mutationの呼出し。通知はlock解放後に発行する。通知処理から同期的に元の保存処理へ戻らない。

読取 → 通知 → 描画の間に相互待ちを作らない。非同期要求には期限を設け、切替・破棄で取消す。期限切れでliveな保存lockを奪ったり、処理途中の保存を強制成功扱いしない。保存待ち超過はbusyとして返し、同じ要求を無制限に積まない。

選択lockと作品lockを一緒に保持して、GUI切替と編集commitを同時に止める設計は採用しない。代わりに、編集受付時に対象ID・base_revisionを固定する。未受付の古いGUI操作はgeneration不一致で捨てる。受付済み編集中に別作品へ切り替えても書込先は変えず、結果には元の対象を明示する。選択変更とcommitの原子的な競合拒否は初期設計の保証に含めない。

同じrequest_idの再送は既存receiptを返す。revision競合は自動上書きや別作品への再適用で解決しない。ユーザーが明示した対象は共有選択より優先する。

## 変更検知と消費電力

ApplicationのAPI処理による保存・共有選択・資産登録・job採用の完了通知を使う。通知は「この対象を再確認」の合図だけでよい。順序番号の永続ログを持たず、通知を失ってもsnapshot再取得で回復する。

通知対象は共有選択、現在作品と資産、必要なjob、作品一覧。APIが成功時に更新する軽量な変更印を補助確認する。作品revisionが変わらない資産登録でも変更印を更新する。ファイルのmtime走査や定期hashは行わない。複数のAPIプロセスからの保存も同じ変更印へ反映し、プロセス内通知だけで同期を保証しない。未選択時は共有選択と一覧の通知だけを扱う。

| 状況 | 補助確認の初期値 |
|---|---|
| GUIが前面 | 15秒ごとにAPI経由で小さい更新印だけ確認 |
| 背面・最小化 | 60秒。変化がなければ素材読取0回 |
| 画面非表示かつ再生・jobなし | 定期確認を停止。復帰時に一度再照合 |
| ウィンドウ復帰・再接続 | 現在選択と受理snapshotを一度再取得 |
| 再生/実行jobあり | 対象session/jobだけ既存の必要な周期で追跡 |

APIの完了通知は150ms程度まとめ、同じ対象の連続通知をdirtyフラグ一つへ集約する。同期読取は同時に一つ。読取中に変更が来たら終了後に一度だけ追いつく。無限の要求queueを作らない。

変更印が変わった対象だけAPIから再取得する。大きな資産はIDが変わったときと実際に必要になったときだけ検証する。通知の取り逃しは補助確認・フォーカス復帰・再接続で回復する。保存後の通知失敗が保存自体の失敗にならないようにし、保存receipt/更新印から再照合できるようにする。

## 重い処理の上限

画像はasset ID単位で一度取得し、host側で表示用の最大1024pxへ縮小する。原本は変更しない。画像cacheは現在対象を含む最大3枚・decoded合計32MiBを目安に、先に達した上限でLRU破棄する。大きなdata URLを再生位置更新のたびにIPCで送り直さない。

波形は元音源hash・対象版・clip・解析versionでcacheする。波形の初回解析はworker/processで一件まで、読み取りをchunk化して取消可能にする。描画用peakは最大800bin。再生位置の移動でpeak解析や全画像decodeを繰り返さない。無変更時の波形生成0回。

音声compile/load/renderは既存の単一audio laneへ送る。同期更新ごとにengineやプラグインを起動しない。重い更新の未開始要求は最新の版一件へ集約する。metadata変更で再生sessionを作り直さない。変更通知、軽量表示、再生停止は重い処理の完了を待たない。

UIの再生head更新は再生中だけ行う。非表示時は描画停止、復帰時に実際の位置を再取得する。停止中に常設のanimation loopを回さない。

## Codexの変更をどう取り込むか

通常は共通Application APIを使う。検証、履歴commit、受理snapshotの更新が終わってから通知する。GUIは受理版の曲情報・画像参照を一括反映する。画像や波形は後から届いても同じ対象keyの補完だけを許す。

## ファイル・core・engineの反映状態

| 変更 | core/engine | GUI |
|---|---|---|
| 曲名・画像 | 文書/資産参照更新のみ | 保存完了後に自動差替え |
| BPM・ノート・FX | 受理版を更新。最新の再生要求でその版をcompile/load | 新しい曲情報。旧版再生中なら「次回再生から反映」 |
| monitor音量 | 対象sessionへ即時command。作品ファイルを変更しない | ackした値を適用済みとする |
| ステム生成・音源差替え | 採用commitの対象/内容hashを更新 | 正しい音源の波形を一度取得 |

engineはplayback_id、project_id、revision/graph hash、apply_request_idで適用を照合する。一致するackが届くまで適用済みにしない。旧protocolで版ackが不十分な場合は送信recordとsessionで照合し、保証不足を明記する。GUIだけ最新版になった状態を実音反映済みと報告しない。

再生中は開始版を保持し、作品変更で勝手に音を差替えない。タイム表示・head・再生用波形は実際のsessionに一致させる。次回再生時に最新の受理版のcompile/loadが失敗したら、古い音へ黙ってfallbackしない。

別作品への選択変更は旧sessionの停止を要求し、ackまで次の再生開始を許可しない。停止失敗時は旧対象を示した停止操作を残す。書き出しjobの対象は受付時に固定し、選択変更で成果物の帰属を変えない。

## 失敗と再取得

状態はempty / loading / ready / staleだけを基本とする。対象不正・削除はemptyに理由、同期失敗はstaleに理由を持つ。取得を失敗しても別作品を自動選択しない。readyになるまで新規再生や対象依存の保存は許可せず、既存sessionへの停止・音量操作は残す。無効なボタンも通常色を保つ。

選択変更でgenerationを進め、旧画像・波形・曲情報を一括で外す。応答時と画像decode完了時にgeneration/対象keyを確認する。同じ作品の更新中は旧snapshotを「更新中」として保ち、一貫した新版へ交換する。外部選択の受信結果をactive_context_setへ書き戻さない。

同期readの期限は5秒、失敗時は1/2/5/15/60秒へbackoffする。復帰・ユーザー操作で即時再確認できる。同じエラーの通知は一件にまとめる。再起動時は受理revisionとengine sessionを確認し、不明な適用を成功扱いしない。

## 段階実装と検証

最初に共通の受理snapshot・対象key・差分取得を作り、既存の2秒全取得を除く。次にAPI完了通知と軽量な補助確認を統合する。最後にengine ack照合を整える。各段階で一つの同期管理経路だけを残す。表示moduleはsnapshot描画のままにする。

機能試験はCodexからのAPI編集、画像だけの変更、A→B→Aの応答逆転、ステム完成、再生中の版更新、停止失敗、保存競合、複数APIプロセスからの変更、通知重複/欠落、再接続、skin切替を対象とする。本番と同じAPIでfixture作品を読み、画像直挿しデモだけで連携を検証済みにしない。

負荷・排他の合格条件（実装後に計測）:

- 10分間の無操作で画像/音声解析0回、文書の全量再取得は復帰等の必要時だけ。前面の補助確認は最大40回、背面は最大10回。
- 1秒に100回の通知でも並列同期readは1件、待機はdirty一件だけ。最終保存へ収束する。
- 保存/選択/停止を並行実行して循環待ち0件。意図的なI/O遅延でもUIイベント処理と停止経路が応答する。
- 画像切替100回後もcache上限を守る。波形解析中の切替で旧結果を採用しない。
- アイドル時のrenderer/core CPU時間、wakeups、RSS、disk/network量を変更前後で比較する。電力は実機で測り、CPUだけから電池消費を断定しない。

正常なローカル通知から軽量表示まで250ms程度を目標とする。これは未計測の目標であり、重い画像/波形の完了保証ではない。診断には検知対象、受理版、engine適用版、GUI対象、直近失敗と各処理時間だけを上限付きで残す。高頻度の全状態ログは出さない。実装状態は [VERIFICATION](../Development/VERIFICATION.md)。
