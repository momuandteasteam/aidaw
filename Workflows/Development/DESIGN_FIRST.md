# 設計を先に確定する

読む条件: 本体の機能追加、バグ修正、挙動変更、依存更新、リファクタリングを始めるとき。
正本範囲: 実装前の設計確定と変更中の再確認手順。
関連要件: 変更対象のR-ID。

## 実行順序（必須）

1. 調査・再現・読み取りを先に行い、対象要件と仕様を所有する文書を選ぶ。この時点では製品コードを変更しない。
2. **先に所有文書を編集する。** 入出力、状態遷移、失敗・取消、互換性、配置・依存、検証条件を必要な範囲で確定する。バグ修正も、再現条件と本来守る不変条件・回帰検証を仕様へ反映する。仕様が既に正しくても不足していた条件・検証根拠を具体化する。
3. 設計内の判断が済んだら `Design status: ready` と記し、`npm --prefix Core run check:docs` を通す。未実装は検証台帳でplannedとする。仕様を確定したことと実装完了を混同しない。ユーザー判断が不可欠な点だけ質問し、通常の設計判断は依頼の範囲で自律的に確定する。
4. 製品コードを触る前に `node Core/Tools/design-gate.mjs begin <作業ID> <所有文書パス...>` を実行する。文書hashと開始時の製品コードhashをCore/Stateへ記録する。成功後に実装・テストへ進む。
5. 実装中に仕様変更が必要なら、製品コードの編集を止めて先に文書を再確定し、同じIDでbeginを再実行する。既存receiptは履歴に保持する。他の作業IDの記録を上書きしない。
6. 対象テストと `node Core/Tools/design-gate.mjs check <作業ID>` を実行する。確定時の文書が変わっていれば再設計する。結果を検証台帳へ反映し、未達を隠さない。次の変更でreadyを実装済みの意味に読み替えない。

正本へ仕様を集約し、作業日誌や同じ設計のコピーをDocsへ増やさない。receiptは運用証跡であり仕様ではない。製品コードより前にbeginした事実の確認は作業履歴とレビューも用いる。後から作ったreceiptで順序を証明したことにしない。

## 適用範囲と機械検査

調査だけ、作品データの編集、文書だけの修正には製品コード用receiptは不要。手順の所有者は本書。一般実装・GUI・セットアップ実装の各入口からここへ進む。

CIのPR差分検査はCore/Source、Core/Tools、Core/Tests、Plugins、Coreの依存・ビルド設定の変更に対し、ArchitectureまたはContractsの文書変更を要求する。これは文書更新の欠落検出であり、設計内容の正しさや編集時系列の証明ではない。順序を守る責任をCI成功で代替しない。
